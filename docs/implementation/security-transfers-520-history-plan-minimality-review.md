# #520 history bridge plan: bounded source-only critique

Reviewed `/workspace/.budget-tools/cloud-control/520-authoritative-history-plan.md` against `docs/product/specs/SPEC-009-corporate.md` §§3, 8, 12, 15, the accepted owner scope in `docs/product/reference-adoption.md:33-39`, and the current trade/cost/position contracts in `/workspace/impl-520-security-transfers`. No runtime or private broker evidence was inspected.

## Recommendation

Do **not** make a new per-security/account zero-opening and complete-through *certificate table* a prerequisite for every native buy/sell history, or reject every date with more than one unit-changing native event. Those are stronger requirements than SPEC-009 and would make the native known-basis path unavailable without establishing extra facts that the accepted design did not ask to persist. Keep the small explicit pair relation, repository-only read bridge, full-lineage replay, CAS/replay on apply, lock checks, and fail-closed treatment of unsupported source facts. A reader can derive a **recorded-ledger** known-basis history from actual live buys and sells under the current canonical cost model, without claiming to prove complete external broker history.

## Evidence and distinction

- SPEC-009 §3 moves **selected remaining** basis/acquisition dates under the existing cost method; §8 says replay acquisitions/disposals/pairs by date and *existing stable order* and explicitly singles out **snapshots and unpaired deliveries** as needing known-basis provenance (`docs/product/specs/SPEC-009-corporate.md:15-17,35-39`). §12 says add only the relation needed to prove pairing (`:53-55`). §15 already accepts the bounded known-basis policy and stage sequence (`:70-76`). The owner decision calls for documented source lots/basis and explicit pairing, while unknown basis and ambiguous legacy pairs remain manual (`docs/product/reference-adoption.md:33-39`). None requires a new completeness-attestation ledger for ordinary recorded buys.
- A native buy stores account, security, date, positive E8 units, gross native amount and fees. The canonical cost engine treats each buy as an acquisition with basis `amountCents + feeCents` (`packages/db/src/repos/trades.ts:31-47,118-120,204-220`; `packages/domain/src/invest/invest.ts:173-197,206-250`). The persisted average/FIFO preference is read by `investmentPreferences` (`packages/db/src/repos/investment-preferences.ts:7-19`). Native buy/sell history can therefore define the application's known analytical lots/pool when replayed from the start of the recorded scope and all intervening unit facts are supported. This does **not** assert that no broker event was omitted or that Gate 3 private reconciliation has passed (`SPEC.md:266-278`).
- The pure helper currently demands `opening: 'documented-zero'` and `historyComplete: true` (`packages/domain/src/invest/security-transfer-replay.ts:22-30,91-100`). That is its present interface, **not** independent evidence that SPEC or the owner requires a physical-zero certificate for native transactions. Do not set those fields by pretending the absence of rows proves physical zero. Instead refine the Stage A/repository contract to distinguish a complete *recorded native ledger lineage* from an externally documented opening, or otherwise give the flags a narrowly defined app-ledger meaning reviewed against the spec. A consistent DB read and fact fingerprint can make the scope complete *within the recorded ledger*; later edits/backdates/undo/imports must invalidate a preview by reread/replay, not necessarily by maintaining a second coverage table.
- The current read order is `(trade.date, trade.id)` (`packages/db/src/repos/trades.ts:370-381`; `packages/db/src/repos/portfolio-summary.ts:476-494`); canonical cost additionally orders same-day buys/deliveries before disposals and preserves input order within that rank (`packages/domain/src/invest/cost.ts:14-29`). Multiple native buys on one day thus have an existing reproducible application order and basis; a buy and sale on one day have the existing buy-first calculation. The plan's blanket one-unit-event-per-day rule conflicts with §8's instruction to reuse that stable order. `sequence` in the pure helper only needs unique, deterministic positions (`security-transfer-replay.ts:17-21,105-112,130-149`); it need not mean externally attested execution time. Do **not** claim `(date,id)` is broker chronology. A new paired transfer interleaved with same-day native events needs the persisted pair creation/order information required by §8; reject only a genuinely order-sensitive case whose position cannot be established without inventing an order.
- The plan correctly rejects nonredundant holding anchors, unknown/null basis, unpaired deliveries, inferred pairs, unsupported currency/corporate events, and stale/locked/insufficient paths. `effectiveSnapshots` may ignore only a numerically redundant snapshot for position cost, but that numerical match alone does not establish transfer ancestry (`packages/db/src/repos/portfolio-summary.ts:305-363`). SPEC-009 §8 explicitly requires provenance for snapshots/unpaired deliveries, and §5 blocks unknown basis (`docs/product/specs/SPEC-009-corporate.md:23-25,35-39`). Do not turn cash opening balance, earliest buy, or a matching snapshot into an external zero-history assertion.
- The plan's blanket split rejection is a separate gap, not a new owner-policy dependency. SPEC-009 retains existing split behavior and AC-009-06 requires correctly scaled units/basis (`docs/product/specs/SPEC-009-corporate.md:21,31-33,57-64`); canonical cost already treats a split as zero-cash unit change with conserved cost (`packages/domain/src/invest/invest.ts:173-197,206-250`). The current pure replay rejects split as unsupported (`security-transfer-replay.ts:18-21,257`), so a buy/sell/pair-only first slice may be explicitly staged, but completion of SPEC-009 must resolve the split path or state the acceptance gap. No new split action or tax policy is implied.

## Minimal implementation direction

Start with a read-only adapter for one security and actual relevant accounts: read live trade history plus holdings, explicit pairs when added, persisted cost preference, account eligibility/locks; verify native trade invariants and no unsupported lineage fact; map recorded buys/sells in canonical deterministic order; derive acquisition basis only from stored amounts/fees; replay and compare resulting units/basis to the canonical position without accepting a snapshot as positive provenance. Return typed unavailable for any gap, ambiguous pair/order, unknown basis, overflow or conflict. Persist only SPEC-009's small 1:1 transfer relation for new pair identity, with a stable position for same-day pair edges. On future apply, atomically reread the full affected lineage and reject a changed preview. This enables a bounded native-history path and leaves imported/legacy unknown anchors for private review. It does not prove actual broker completeness or authorize formula/default changes.

Multiple native events on a day need no new product rule. Selected-method comparison is per account, not only aggregate basis. Canonical snapshot redundancy is corroboration, never invented acquisition ancestry; effective anchors and unsupported legacy facts remain unavailable.
- Pair ordering remains tied to explicit persisted pair identity/order. Mixed native/pair days require a proven compatible relative order or equivalent outcomes; the bounded fallback is typed ambiguity. The asOf prefix alone must not later be described as a proven intra-day placement when that mixed-order proof is absent. Stage A source work does not add pair persistence or guess old links.
- Raised one ambiguity during this review: an asOf-only reader fingerprint could not be compared directly to a latest-history apply fingerprint when later events already existed. The author corrected the plan: a single snapshot reads/classifies the full currently recorded affected history, `replayThrough = asOf` selects the preview prefix, and `fingerprintThrough` covers the latest relevant facts including the suffix. Future apply recomputes that same full-scope fingerprint, then replays the proposed transfer and later suffix. This closes the design finding. Coverage-date and event-date consistency must be enforced in the helper; the future apply must discover newly added later facts rather than querying only the old fingerprint boundary.
- Split remains a declared AC-009-06 gap, not a request for new tax/product policy. Typed unavailable is acceptable for this staged reader slice; it is not evidence that full SPEC-009 split acceptance has passed. No certificate table, mutable lot ledger or financial writer is required for the proposed native diagnostic bridge.
