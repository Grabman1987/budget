## Finding

**P2 — DELETE can bypass the reviewed-state token while still deleting a changed never-assigned payment.** `apps/server/src/api/schemas.ts:404-409` makes `reviewToken` optional, the route forwards that optional value (`apps/server/src/api/expected.ts:270-279`), and `packages/db/src/repos/expected.ts:459-474` calls `assertPaymentReview` only when a token is supplied. The new UI supplies one, but the public DELETE route remains valid without it. Source-level case: client A reviews an unassigned payment; client B changes its name, schedule, future amount version, or pause; client A (or an older client) sends `DELETE /api/expected/:id` without a token. The current lifetime-assignment proof still returns `neverAssigned`, so deletion succeeds despite the changed reviewed object and removes its eligible future open occurrences. This defeats the claimed CAS guard for an explicit lifecycle action, though it does **not** bypass the lifetime-assignment prohibition. Minimal fix: require the digest on the HTTP DELETE request and compare it unconditionally in the writer, with any truly internal legacy caller given an explicit separate contract rather than silently omitting CAS.
