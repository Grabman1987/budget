## Storage and date semantics

`security_exposure_version` identifies one security's inclusive `valid_from`, `complete`, `source`, creation timestamp and audit group. Its members in `security_asset_exposure` carry security, class, integer `weight_bp`, effective date, source and audit fields. One version per security/day; one member per class/version. Positive weights total exactly 10000 for a complete set. An explicitly incomplete set may total 0–10000; the remainder belongs to the visible unclassified bucket. Empty incomplete sets allow a dated transition to unknown classification.

`exposuresAsOf(db, day)` is the only date resolver: latest whole version with `valid_from <= day`. `assetExposureOfSecurityAsOf` delegates to it. Future versions cannot affect current reads. Before the first version, all value is unclassified. There is no timeless fallback. Same-day replacement is atomic and audited: previous member snapshots remain in `audit_log`, so grouped undo/redo restores their exact identities, source, dates, weights and timestamps. Single-entry exposure undo is refused, including forced undo; post-undo invariants run in the same savepoint.

The legacy `security.asset_class_id` column remains readable metadata for backward compatibility. Single-class instrument saves continue to write it and also write a 10000-bp version. Weighted API writes do not pretend that a mixed product has one class. Valuation, class performance, allocation, R13, rebalancing, savings proposals and export class labels use the resolver, never this column. The instrument form sends classification only when the owner changes it or its effective date; renaming a mixed instrument preserves its exposure. The existing editor exposes the effective date, defaulting to the Vienna day. No settings-page implementation is included.

Migration `0030_security_asset_exposure.sql` is generated by Drizzle; the appended data seed is reviewed SQL. Every existing non-null legacy assignment, including retained securities, becomes a 10000-bp set. Effective date = earliest stored trade or holding date (including retained source records), otherwise the security creation day. Source `legacy_assumed_from_first_record` deliberately identifies an assumption made to preserve existing class values; the first ledger record does **not** prove the classification was known then. No certainty is invented. Earlier dates remain unknown. Null assignments remain unknown. Source rows, prices, trades, holdings, balances and target versions are untouched. The Drizzle migration journal makes application idempotent.

Weighted market values use pure `splitAssetExposure`, BigInt products and largest remainder, ties by sorted class id. Each account/security valuation is the conserved atom; every consumer aggregates those same slices. Signed values and unknown remainders also conserve cents. Regions still split the whole product value using the unchanged `regionsJson` mechanism. Class-performance histories split values and security cash flows at their own dates; classification changes transfer value between class sleeves rather than becoming artificial investment returns.

Savings plans remain actual whole-instrument schedules. A mixed plan is eligible for each class in proportion to its weights, and cannot be paused for R13 solely because one sleeve is overweight while another is underweight/unmanaged. Freed capital remains conserved across real plan ids. Risk thresholds, speculative kinds, leverage, target semantics, allocation quality and universe are deferred to PR2/PR3.

## API

- `GET /api/securities/:id/exposures?asOf=YYYY-MM-DD`: effective set (`validFrom`, `complete`, `source`, `weights`); default as-of = Vienna today. Missing history yields an incomplete unknown set.
- `PUT /api/securities/:id/exposures`: `{ validFrom?, complete, source, weights: [{ assetClassId, weightBp }] }`. At most 50 distinct active classes, positive integer weights, bounded nonblank source, real calendar date and exact complete sum validated on the server. Default date = Vienna today. Returns `{ exposure, groupId }`.
- Existing security POST/PATCH accepts optional `exposureValidFrom` with `assetClassId`; grouped metadata/exposure write and undo are atomic. Null class produces an empty incomplete version.
- Existing `POST /api/undo` reverts exposure groups; its returned group can be undone for redo.

All routes remain behind the existing session and origin guards. No new step-up exemption, provider request, dependency or automated booking is introduced. New exposure errors are German and omit database identifiers.

The stepped-up ZIP now includes `security_exposure_versions.csv` (including empty/incomplete sets) and `security_asset_exposures.csv` (full weighted history); current class labels resolve on the export date. Audit/session data stay excluded.

Exposure change and same-day replacement tests compare exact rows after undo/redo. Automated evidence is synthetic local evidence, not production reconciliation.
