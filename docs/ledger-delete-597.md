## Implementation and limits

The existing ownership reader has an explicit delete policy; the default update policy is unchanged. Delete excludes reconciled, actual contact/trade-settlement-owned, document/statement-protected and invalid rows. Contact preflight calls the same existing assertContactBookingWrite guard as the canonical writer, including later write-offs; an unsettled contact split alone does not block deletion. Transfer pairs, ordinary bank references, payroll links and expected-payment links retain the canonical delete writer's existing semantics. The original relatedTransferBookings helper retains its direct incident-neighbour semantics. A distinct connectedTransferBookings traversal is used only for atomic deletion/restore and their full-group reads/checks, so these operations resolve the same full identities from any leaf. A two-transfer-split parent and both counterpart leaves are one three-booking component. Preview caches each discovered component for this read and includes every unselected side; transfer count follows actual distinct transfer IDs. A protected or missing partner excludes the entire pair. At most 500 affected booking sides are accepted; no partial pair is written to fit a limit. Selected and actual deletion native totals are distinct and use integer cents with explicit unavailable sums.

The existing `/bookings/bulk` path always recomputes eligibility in its locked transaction. New GUI callers must submit the exact preview revision; omission remains compatible for legacy callers but never bypasses eligibility, locks or pair protection. The legacy trade rejection code remains `invalid`, preserving its existing API contract; previewed callers receive the named `linked_trade` reason. The source fingerprint includes selected/affected IDs, complete current row/split states, ownership facts and a conservative global audit-head ABA fence. Any audited write, including Undo, can require a new confirmation. A stale submitted revision returns 409 before any write or audit. No second writer route or mutation framework exists.

The canonical `deleteBooking` writer performs each eligible deletion, preserving its transfer/expected-link changes, audit and Undo. One bulk audit group covers actual changes. Result IDs include any unselected counterpart actually deleted. Single GUI deletion also submits a source revision. Protected single-booking confirmation uses the existing form alert-dialog/focus scope, now trapping Tab/Shift+Tab in whichever alert dialog is visible; the draft and ordinary close/discard guard stay mounted. Bulk confirmation uses the existing bounded FormDialog with error/reload/explicit reconfirmation. Both reuse shared privacy-aware native formatting and design tokens.
