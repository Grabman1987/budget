# Toolkit for YNAB source review notes

Scope: read-only review of the Toolkit source at `631c914714e747e0b4478e3ac521057761622bcd` (2026-09-09), focused on the README, generated feature list/settings registry, general/accounts/budget features, architecture, dependencies, tests, and fit against Budget's current SPEC/DESIGN. No extension was installed; no personal browser or YNAB account was opened. The lead supplied fresh, generic YNAB observations: native Plan now has progress-bar On/Off controls, custom focused views, a target/expected-income monthly summary, and a target inspector. ## Source and count interpretation

- README.md:7-9 explicitly says Toolkit is in maintenance mode; updates will be infrequent and likely bug fixes, with maintainers sought. This source snapshot is not evidence of current release/store compatibility beyond that statement.
- README.md:20-24 points to `docs/feature-list.md`, which is generated. That document has 96 `##` feature entries by a simple heading count. The source tree has 101 `settings.js` files, but settings files can export arrays and hidden settings, so files, feature classes, and user-visible controls are not one-to-one. `scripts/generateSettings.js` filters `hidden: true`; `docs/development.md` says generated artifacts are regenerated by `yarn gen`. Do not treat the README as a promise that every feature is currently functional or separately selectable.
- `src/extension/features/**/settings.js` is the per-option registry. The `defaultFeatures` package list is a warning allowlist, not a default override; three obsolete names remain there. The type declaration supports checkbox/select/color/system types, but the actual enumeration found no system setting. Hidden examples include `AutoDistributeSplits`, `SpareChange`, `StealingFromFuture`, `TargetBalanceWarning`, and hidden row-color child settings. The generator has migrations for historical names (`ConfirmEditTransactionCancellation`, `ToggleMasterCategories`, `LiveOnLastMonthsIncome`, `ReconcileAssistant`); there is no explicit deprecated/incompatible metadata field. Hidden/migrated must not be presented as currently supported visible controls. The lead's [enumeration](toolkit-coverage.txt) supersedes preliminary counts/default interpretations in review notes.
- Selects, child color settings, and coupled features create conditions. Examples: `Pacing` can invoke `BudgetProgressBars`; `SubtractUpcomingFromAvailable` incorporates `ShowAvailableAfterSavings` and can exclude card-payment amounts; `DisplayUpcomingAmountColor` is only useful with the upcoming-total display. Confirm active combinations against the source/real app before treating them as independent requirements.

## Framework/runtime dependency and maintenance

Toolkit is a WebExtension content script for `app.ynab.com`, not a standalone budgeting UI. `src/manifest.json` targets YNAB domains and declares only `storage`; the bridge injects the bundle into the YNAB page context. `docs/architecture.md` describes one global MutationObserver and Ember route observers; `docs/ynab-internals.md` says the app is a closed-source Ember SPA and Toolkit relies on undocumented `window.YNAB`, Ember DI/service/controller/component lookups, jQuery `$`, current DOM class names and handwritten reverse-engineered types. It explicitly warns these can change without notice and says verify each dependency live. This is a direct compatibility and support risk, not reusable Budget architecture.

Feature execution is route/mutation gated (`src/extension/features/feature.ts`, `src/extension/ynab-toolkit.tsx`). The architecture doc notes `observe()` is called for every relevant DOM mutation and is not automatically gated by `shouldInvoke()`; each feature must gate its own work. Changes can silently become no-ops or fail when YNAB renames selectors/services. No Toolkit option should be treated as distinct from YNAB's current native behavior merely because an implementation remains in this snapshot.

Settings default to extension `browser.storage.local` (`src/core/common/storage/index.ts`, `StorageArea.Local`); additional Toolkit state is also stored in YNAB-origin localStorage (`src/extension/utils/toolkit.ts`). Therefore settings/state are browser-profile/origin specific, not a Budget cross-device preference contract. The option schema and documentation are English; feature selectors often depend on labels or internal class names, so app locale and responsive DOM variations need validation.

README.md:35-38 documents Chrome/Firefox/Edge availability and no Safari support. `docs/testing.md` covers manual Chrome/Firefox extension loading and leaves Edge `TODO`. `package.json` uses Yarn 1.22.19, Node >=24 and an older extension stack (React 18, jQuery, Moment, Highcharts 9, `core-js` 2, Babel/Webpack). Tests are Jest/jsdom with mocked YNAB services; only 13 test/spec files exist under `src/extension/features` at this commit. That is not live-YNAB integration coverage. No build/tests were run in this scoped source review.

## Fit against Budget's accepted design and behavior

Budget's controlling design is its own: SPEC.md:1-47 owner overrides and SPEC.md:66 source precedence keep the prototype/DESIGN tokens authoritative. Budget is a private single-user app with a purpose-built Blaupause system, accessible React components, integer-cent domain rules, server read models, audited writes, locks and undo. It does not run inside a third-party DOM. The general navigation/details policy in SPEC.md:29-35 retires generic detail drawers/sidebars, with narrow exceptions for Plan › Monat inspector (#446) and global-search palette (#484; SPEC.md:25-29). Toolkit's YNAB-side UI surgery is therefore a reference for a task pattern, never a design implementation source.

Candidate patterns worth retaining only when tied to a real Budget gap:

- Read-only filters, focused views, compact lists, and bulk selection can reduce work in large registers. Budget already has `/konten/buchungen` filters and multi-select actions (`apps/web/src/ledger/bookings-page.tsx`, `booking-table.tsx`); it currently supports category assignment and mark-as-checked. Additional bulk fields such as date/memo/payee could be considered only through the existing audited API, reconciliation-lock checks, grouped undo, and explicit selection. Toolkit's DOM event shortcuts are not portable.
- Reconciliation-assistant math could be a read-only suggestion if owner evidence shows a real need. Budget currently has an explicit reconcile flow and its owner-defined “duplicate exact amount” / “missing entry” cases; suggestions must not post adjustments, alter cleared status or bypass account locks. Any algorithm needs its own false-positive and cent-exact acceptance contract.
- Split keyboard flow/autofill is a usability reference, but Budget's booking-line directive already requires exact gross-line rest, zero-rest save guard, largest-remainder cents, audit and undo. Consider only a concrete field-navigation gap; never import implicit balance-writing behavior.

Patterns that are already provided or conflict with Budget's decisions:

- Privacy Mode, hidden account balances, hidden closed accounts, and sidebar import/uncleared highlighting largely overlap existing amount privacy, account hierarchy, account status/reminders and inbox. Budget design uses status evidence and selective warnings, not replicated badges (`DESIGN.md` Konten / Seitenleiste and SPEC owner directives).
- Native YNAB now has progress bars, focused views, target/expected-income summary, and target inspector per lead-provided generic observation. Toolkit `BudgetProgressBars`, category filtering, `DisplayTotalMonthlyGoals`, target indicators and target columns may duplicate or replace native behavior; verify current native version/platform before proposing. Budget already owns the Plan grid, target progress and inspector under SPEC.md:21-29 and DESIGN.md Plan section.
- Per-row height, stripes, font, currency colors, colored master rows, negative-color rules, emoji, compact headers, icon sizing, scrollbars, print CSS, column order and inspector collapse are visual-only YNAB-specific overrides. They conflict with Budget's blueprint typography/tokens, hatching and semantic color rules, mobile layout, custom components, and accessibility baseline; do not transfer as product requirements.
- “Subtract upcoming transactions from Available”, “Available After Savings”, and total upcoming overlays redefine or layer over envelope figures using heuristic category-name rules. Budget keeps Available as a cent-exact assigned/activity/rollover figure and recurring/event projections separate; subtracting reservations into Available risks double-counting and violates the fixed calculation/read-model boundary. Today already uses a selected horizon and a dedicated due list (SPEC.md:17).
- Pacing and “Days of Buffering” calculate a YNAB-specific view of category/month pace or budget cash versus average historical outflow. Budget already has one governed pace/read-model, free-to-payday lead, explicit liquidity forecast and fixed KPI placements. A new runway metric would need an explicit KPI formula/scope decision; avoid importing the extension's defaults.
- Auto-mark-as-cleared, save-on-enter variants, card-payment assist/rectification, “spare change,” automatic split edits or any direct account/category changes affect financial state. Budget requires explicit capture status, audited writes, cent guards, reconciliation locks and undo. Owner directive #499: new cash capture is confirmed; bank capture stays pending with manual confirmation. No automation should infer that cash/bank lifecycle beyond the existing rule.
- Markdown in notes/memos is a security and escaping decision, not styling. Budget should preserve plain text unless a safe renderer is explicitly scoped; no HTML injection.

## Coverage and remaining uncertainty

The source/doc review covered README and generated feature list plus registry implementation, architecture and YNAB-internals documentation, dependencies, storage, manifest, tests and representative feature code for hidden/coupled settings. It did not enumerate the row-level `toolkit.csv`, run the generator, build the extension, test current YNAB behavior, inspect authenticated pages, or claim feature-by-feature runtime parity. The README itself says active maintainers are being sought; feature/store behavior may lag. Before adopting any runtime-specific interaction, require a live compatibility check against the current supported YNAB version and a non-privileged isolated browser scenario. For Budget, implement only the underlying user problem through its own models/routes/components and acceptance constraints.
