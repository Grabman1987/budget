## Existing implementation and precise gaps

1. **Goal CRUD and source progress exist.** `packages/db/src/repos/goals.ts` validates one category OR account, positive target, and uses audited transactional create/update. `listGoals` derives category progress from `budget(...).availableCents`, average of three assignments, or account cash growth. Dates and links may be null; multiple goals per source are allowed. Goal create/edit currently writes no category target. `/api/goals/:id/adopt` separately calls `setCategoryTarget` with a versioned `by_date` target. UI still offers that button in BOTH `budget/goals-panel.tsx` and `budget/plan-panel-pages.tsx`.
2. **Two different rates are intentional existing calculations.** `domain/goals/goals.ts` uses month-end available, then months AFTER the viewed month. `domain/ledger/targets.ts` uses opening carry and includes the viewed month; `goalCents` is its total monthly target and `needCents` subtracts current assignments. Literal example: target 120000, October carry/assigned/activity all 0, due December => goal future rate 60000 (November/December), Plan by-date monthly target 40000 (October/November/December). Thus auto-adopt alone fails same-rate AC. After partial assignment `goalCents` and remaining `needCents` also differ; do not label both as the same rate or repeatedly add a full already-funded rate.
3. **Assignment machinery exists, not the goal action.** `repos/budget.ts:assignMany/moveMoney/quickAssignMany`, `guardAssignable`, `repos/envelopes.ts:setAssigned`, `/api/budget/:month/{assigned,move,quick-assign}`, and `useBudgetWrite` provide integer cents, transactional audit group, cent guard, shared invalidation and Undo/Redo. Goal list/detail have no Rate zuweisen. `moveMoney(null,category,amount)` is additive; `assignMany` receives absolute resulting assignment. Never confuse the two or overwrite an existing assignment with the delta.
4. **Ist and dashed Soll already exist.** `pages/goals-progress-report.tsx:GoalHistory` uses shared Line kind=actual/plan, chart tooltip/accessibility primitives and report data; Plan detail already reuses it. `repos/goals.ts:goalsReport` computes category month-end history, but starts at `createdAt` month, clamps negative available to 0 and ends actual at today’s month. Newly created goal with six preceding category months therefore gets one current actual point, not six. There is no start field in DB/API/editor. Its report endpoint ignores selected `month` while goal rows use selected month: current detail explicitly labels a separate history stand; do not silently mix the two when revising this UI. Existing missing/duplicate-source/non-EUR report guards must remain.
5. **Grouping is only current status.** `goals-model.ts:goalGroups` returns Offen then Erreicht. `goalProgress` drops a previously reached goal back to behind/on_track after spending. `savings_goal` only has name/amount/date/category/account/note/timestamps: no reached/completed/start metadata and no completion writer. A durable user action Abschließen cannot safely be represented by delete, a note convention, local storage or a read-side mutation. Goals and bookings must remain accessible.
6. **Detail routine remains unfinished.** `GoalDetailPage` and report `GoalDetail` supply several headings/links/visible explanation blocks, edit/adopt actions, but no P11 next-step action section. Preserve route ID, selected month, `quelle=report` return and editor return focus while giving Plan its one title/back and an explanation disclosure; avoid accidentally altering the report variant by unconditionally changing a shared component.

## Decisions not established by the owner text or current model

- **Current-month versus future rate:** establish the same displayed target/rate and whether Rate zuweisen means the remaining current-month need (recommended existing Plan semantics). The 120000/December example above makes the choice concrete. Blindly switching `goalProgress` breaks existing independently specified future-rate expectations; freezing that rate as a monthly target only at save drifts as time/balances change.
- **History start:** “ab Zielbeginn” plus “newly created goal with six history months” needs a real definition. Existing createdAt is not backdated goal start, and prototype start is independent. Do not rewrite createdAt, assume a fixed six-month window, or silently use all category history as the goal’s start. Existing goal history from creation can remain until a start/backfill rule is settled.
- **Lifecycle trigger:** after reaching, which spending qualifies (any outgoing amount, only spending that drops below target, historical month-end or same-day reaching/spending), and how do edited goals/undo reopen? Monthly end balances alone cannot prove a same-month reach-then-spend event. Explicit completion persistence is absent; reached-before-spending needs proven history, not merely current balance below target. Account goals and undated goals must be retained even if category actions are unavailable.
- **Competing/source-changing goals:** several goals currently can share a category. One category target cannot simultaneously equal different rates. The report already declares this ambiguous. No first/last-goal wins, summed-target allocation, destructive unlink cleanup or uniqueness migration is authorized. Define a supported primary/eligibility rule before automatic writes for those existing cases; never silently overwrite an unrelated manually versioned target when moving a goal to another source.

These are concrete model/financial choices, not a request to revisit the already approved table, actions or grouping wording. Root can progress the determinate UI/read seams while retaining these as explicit incomplete AC; a complete #604 financial slice should not claim acceptance until they are resolved.
