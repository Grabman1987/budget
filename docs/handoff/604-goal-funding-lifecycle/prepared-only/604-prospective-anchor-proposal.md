# #604 — smallest prospective evidence anchor (proposal only)

Source basis: reviewed source checkpoint 92bf1874; no migration/schema/source expansion has been applied here. Existing seeded/imported databases contain unaudited baseline rows (`packages/fixtures/src/seed.ts:58–75` intentionally leaves audit empty). Requiring an empty reverse basis therefore excludes new goals there too. Normal account/category UI creation uses createEntity/insertTracked, but that does not repair an existing unaudited seed.

## One additive audited goal field, one existing endpoint seam

Recommend a nullable, versioned `lifecycle_anchor_json` field on savings_goal (migration48 only if Root authorizes extending its currently unintegrated scope). It contains schema version, goal intent digest (goal/source/threshold/start), explicit Vienna day, high-water audit rowid, exact projected financial-source fingerprint and the canonical actual available amount at that instant. No raw transactions, audit snapshots or private text need be duplicated into the field or API. Read-side snapshot reconstruction remains local.

Create the anchor at the end of the existing authenticated `/api/goals` create command, inside the same transaction/audit group, after the safe category target synchronization. Actual non-test repository call-site search finds createGoal/updateGoal only in these goal routes. Existing amount/date/category/start edits replace the anchor prospectively; unrelated name/note changes preserve it. There are no automatic anchors on GET, imports, old goal rows or migration upgrade. An old goal without an anchor stays unavailable unless an explicit future action creates a new prospective basis. No financial history is backfilled and a selectable historical start still affects the history graph only; the anchor never claims proof before its real capture day.

The fingerprint is a deterministic sorted projection of the exact financial columns already read by goal-lifecycle.ts, not a database-wide file hash. Canonical `budgetOfLedger(...,{asOf: anchorDay})` supplies the initial amount. The audit high-water mark is recorded before updateTracked writes the anchor intent; later read validation requires the anchor's own audit group to exist completely and rejects source-table writes in that same group after capture. This guards a future nested/composed repository caller from turning an intermediate state into a commit proof. Current public goal callers change goal metadata/category targets only, not ledger source rows.

## Replay strictly after a proven current-state anchor

1. Load current projected source and all relevant retained audit/ancestry after the anchor watermark within the existing bounds.
2. Reverse the post-anchor audited changes and compare the reconstructed basis fingerprint with the stored anchor. This allows the unchanged unaudited seed because it is explicitly witnessed now, not dated retroactively. A later unaudited source change cannot round-trip to the anchored fingerprint and fails closed.
3. Validate the persisted anchor intent and exact recorded row/group against the currently selected goal, then seed the pure point chain with the canonical anchored amount at its actual day. If below target, only a subsequent complete audited boundary can prove reaching; if already above target, reaching is proven from the anchor day, never before it.
4. Replay surviving post-anchor complete original groups using the existing canonical mapper and budget/activity functions. A later real newly recorded expense completes the goal; expense and reaching in one group still do not establish an intermediate committed state. Same-day ordering is the audited group boundary order.
5. Preserve current whole-group consistency, created booking+split guard, status-independent economic signatures, expense financial dates, earliest qualifying event, actual-as-of and work bounds. Pre-entered future expenses remain a separately disclosed gap; no new generic financial event hooks.
6. Undo/Redo of post-anchor funding/expense groups uses the existing active-original graph and rebuilds the derived lifecycle. Undoing anchor creation removes/restores the audited intent with the goal group. A post-anchor Undo referencing pre-anchor financial evidence cannot safely retain its old reach proof: return unavailable unless the original anchored state plus a complete resolved ancestry can be reconstructed. Do not silently call such a pre-anchor reversal a new funding event. This limited older-history case must remain an explicit gap if not fully implemented.
