# #604 — selected implementation dataflow

Read-only proposal after owner's three answers, 2026-10-21. No source changes or runtime. Migration48 is reserved for604;47 already exists. This resolves the previous alternative designs: **derive automatic lifecycle from retained source/audit evidence at one shared read seam; persist only new user intent. Do not add automatic completion hooks to financial writers.**

## Why this seam matches the actual repository

`repos/types.ts:runInTransaction` merely calls db.transaction and has no operation context or outermost-commit hook. Some callers use db.transaction directly. `setAssigned` runs inside assignMany/moveMoney/category merge; observing it would see intermediate states (including duplicate absolute assignments in one group). `assertLedgerInvariants` also runs within composed operations and is not called by importBooking before return. Neither is a safe universal lifecycle-finalization hook. Changing them would spread604 across unrelated money writers and risk treating transient state as reached.

Every tracked change instead already records full SQL-column before/after snapshots in `audit_log`, with group_id and explicit undo_of_id. `audit.ts:history/loadTarget` intentionally order by SQLite rowid, not timestamps/UUIDs. Undo entries store snapshots and reference the entry reverted; redo is an Undo of that Undo. Current `listGoals` supplies getGoal and goalsReport, so **listGoals→readGoalLifecycles** is the single insertion/read seam. The returned lifecycle is a derived DTO and never writes during GET. Existing money writers and Undo remain unchanged.

## Concrete automatic proof algorithm

1. Load goals once. Source key is category/account plus current target intent and effective start. Load current ledger source rows and relevant retained audit entries once for the request, including full groups and Undo ancestry; use rowid as the audit sequence. Read snapshots locally only; expose no raw audit bodies in the API. Maintain immutable raw-row maps for account/category/booking/booking_split/envelope_month/budget_month (the actual sources used by budgetLedger). Soft-deleted retained rows and before snapshots matter for reverse reconstruction.
2. Reuse the canonical ledger row→BudgetInput mapping from `queries.ts:readBudgetLedger`; extract that mapping into a pure helper callable by both existing live read and reconstructed snapshots. Preserve transfer-partner resolution, split amounts/status, account opening/onBudget, category opening/rollover, assignment and held values exactly. Do not replace this with a hand-written available=assigned−spending engine. `budgetOfLedger` and `budgetActivityOfLedger` then remain sole arithmetic/classification authorities. The live reader's existing SQL selection behavior must remain identical after extraction.
3. Determine active original audit operations using the actual undo_of_id graph, not action text or money differences. Repeated Undo/Redo can reactivate an original; partial/group reversals must be resolved per entry. Require complete ancestry and coherent snapshots, and verify the reconstructed final relevant state equals the current loaded source state. Invalid/missing ancestry or an inconsistent snapshot chain means that segment is unproven, not a guessed lifecycle.
4. Reconstruct/evaluate only **complete coherent group boundaries**, never intermediate booking-without-splits or one leg of a move. Capture canonical available for a source after a group and attributable real expenses from a later group. One group containing both funding and spending does not itself prove which committed state occurred first; use its before/after states and conservative evidence. `groupId` is NOT a transaction sequence: month-close assigned API can reuse an earlier group ID. Repeated/noncontiguous group IDs cannot be split into asserted commits from timestamp gaps; mark intra-group order unavailable unless another independent proof exists. This is a reason to avoid write hooks, not to mutate existing group semantics.
5. A valid reach proof is canonical available≥target at a proven boundary or a complete prior month-end. A qualifying completion event is the first later surviving attributable real expense, not an assignment reduction, target change, raw negative cash transfer, card-reserve or unfunded-card synthetic term. Reuse `BudgetActivityItem.kind='booking'` together with its underlying booking/split classification and negative source amount. Respect existing booking status/budget inclusion; no new pending/confirmed money rule. Exclude future-dated activity beyond the view's as-of day. Use financial dates first; where dates tie, retained committed audit order may prove the recorded sequence. Never fabricate an assignment booking date or sort UUIDs to invent chronology.
6. Same-month example is supported directly: audit groupA sets category funding to120000, complete canonical state reaches120000; later groupB records a category expense1000. Result is completed even with119000 remaining; if a larger initial amount leaves130000 after expense it still completes. Assignment-only groupB reducing funding is NOT completion. A later actual expense can complete after such a reduction if the reach proof remains active.
7. Undo removes the corresponding active proof: undo expenseB returns reached/open as justified; undo fundingA invalidates its reach and therefore dependent automatic completion even if expenseB survives. Redo reinstates the proof only when the audited source chain is coherent. This works by recomputation, with no automatic marker left stranded and no extra financial group to Undo. An ordinary later assignment reduction is not the same as Undo of the original proof. Changing source/target/start rebuilds proofs for that intent; do not reuse evidence from another category/goal threshold.
8. Legacy/import history can prove prior month-end reaching and a later dated expense through canonical surviving facts. Same-day or same-month legacy states without retained ordering are unproven and expose that reason, retaining manual completion. Never claim history completeness merely because current available once exceeded the target. If efficient bounds are exceeded, return explicit unavailable lifecycle while retaining actual current amounts/manual action; do not silently truncate into a false first expense. Preselect relevant source/month/group candidates, reuse input loads and memoized month projections, rather than query/rebuild the full database once per goal/day. No temporary DB writes or migration execution are involved in reads.

This is a bounded evidence replay adapter, not a new ledger engine. Implementation should first prove the assignment→expense→Undo case with a literal source example, then add relevant metadata/booking changes. If coherent group replay cannot be established for a case, it remains unproven; the implementation must not disguise a monthly-end-only shortcut as complete same-month support.
