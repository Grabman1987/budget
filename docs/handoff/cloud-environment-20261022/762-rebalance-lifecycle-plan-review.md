## Recommended minimum

Keep ordinary actual trade capture in the existing TradePanel/API/writer. Add a bounded audited rebalance event, explicit links to existing actual buy/sell trades, review/close actions and an honest projected remainder. A duplicate full trading form or automatic proposal-to-trade writer is unnecessary for this slice. A normal trade save and a later link are two explicit actions with their own Undo groups: undoing attribution must not silently undo a separately recorded actual trade. If an atomic create-and-link convenience is added later, it must reuse createTrade with one group rather than duplicate its ledger rules.

One strict versioned app_setting record per decision month is adequate without a new schema migration, provided the following contracts are made concrete. Its key must fit app_setting's 64-character limit. GET derives status and never creates an event or trade.

## Corrections required in the plan

1. **Separate proposal freshness from actual evidence.** Section 4 currently reloads complete valuation/quote evidence and rejects stale/incomplete evidence before either actual recording or existing-trade linkage. This is too broad. `trades.ts::createTrade` records user-confirmed actual quantities/gross/fees/taxes and enforces settlement invariants; it does not require a current market quote. Missing quote/FX, changed config or a newer binding decision should invalidate a suggested remainder and require review of proposed next purchases. They must not alone prevent recording or explicitly attributing an already-executed old trade. The event must preserve the binding/proposal snapshot being attributed and display any current mismatch separately. A source quote proves neither execution nor paid price. Do not stamp actual execution “verified” based on a feed.

2. **Use a stable month identity, plus a separate revision of the decision.** One event per decision month prevents trend correction from creating a second trigger. Bind its proposal to the retained decision fingerprint **and decision audit revision**, so same-facts Undo/re-record is visible; the pure display ID `${effectiveDate}:${trend}` is not durable identity. Updating the binding snapshot must not erase actual linked trades or outcomes. A missing event row with retained event audit history is an undone/reviewable event, not a brand-new automatic due trigger. Closing/completion should preserve that identity. No new catch-up trigger policy is needed.

3. **Current JSON plus audit count is CAS, not durable request idempotency.** `appSetting` has no deleted_at; `audit.ts::revertEntry`/`revertCreations` physically remove a created setting on Undo, and undoing an update restores the old JSON. Thus per-leg receipts stored only in that JSON disappear or roll back. Same-key retry after Undo can otherwise be mistaken for a new action. Before mutation, resolve request ID/intent from retained audit evidence as well as current state, within a bounded read. Same intent returns the existing/undone outcome without replaying; changed intent conflicts. Keep the semantic intent hash independent of refreshed CAS and source tokens. Include event identity/action and actual trade identity in that hash. Existing trade importKey is not a replacement for this contract. With link-only scope this protection prevents unintended re-linking; if trade creation is later included it also prevents duplicate financial writes.

4. **Enforce attribution across events, including restoration.** “Unlinked” must mean absent from every live event's effective linked-trade set, not just absent from this month or the latest twelve events. Check that condition in the same transaction as linking. Example requiring explicit handling: link trade T to month A; undo A's link; link T to B; redo A. Generic app_setting restoration does not automatically inspect B. Either add the narrow post-Undo invariant (including force) or derive a cross-event duplicate conflict on read and mark *all* affected events needs_reconciliation. Neither may remain falsely completed or count the same trade as clean execution twice. A new relation is not required solely for this small event set: bounded full-prefix reads are sufficient, with explicit refusal on incomplete/oversized evidence. Do not invent a permanent historical reservation policy that prevents a deliberate corrected attribution forever.

5. **A linked trade remains authoritative outside the event.** Retain the reviewed economic snapshot and its latest audit revision: account, security, kind, date, units, gross/fees/taxes, deletion state and settlement linkage. Compare it with the live trade on each event read/action; economic edit/delete and Undo/redo ABA make the old review stale. Ignore incidental display metadata unless materially relevant. Also verify existing trade/settlement invariants before accepting a link. Generic trade capture/edit remains available; an event status must downgrade rather than overwrite actual facts. A fresh explicit review may accept changed facts. Do not infer identity from matching amount/date or count stale snapshots as additional holdings.

6. **Use separate CAS scopes.** Link/close commands need the event history revision, reviewed actual trade facts/audit revision, and cross-event attribution checks. They do not need a current quote. A proposal review needs exact canonical valuation inputs and their provenance: amounts/units, account/cash/manual valuation inputs, dated price/FX, exposure/classification/config and binding-decision revisions—not merely displayed quote dates or a rounded total. Recompute and compare this proposal evidence inside the same transaction if such a review is stored. Prices/FX may invalidate the advisory remainder without changing historical actual links. Default missing provider stays unavailable for new signals; already retained decisions/events remain readable.

## Minimal implementation sequence

1. Strict event/intent schemas and deterministic read projection: stable month key, retained proposal, audited revision, live reviewed links, reconciliation state, explicit incomplete/remainder-unavailable state. No new trade writer.
2. Transactional explicit link/review/close facade using authenticated/CSRF-protected existing shell boundaries and bounded bodies. Include audit-retained idempotency and cross-event checks from the start.
3. Reuse the ordinary trade dialog for actual input and provide explicit existing-trade selection in the event. Make status/Undo labels reflect whether an action changes attribution or the ledger. A suggested amount or estimated tax must never silently populate confirmed actual evidence.
4. Completion is owner confirmation of the actual leg list and declared outcome, not numerical proximity to targets. If the current deviation cannot be valued, show that fact rather than blocking historical recording or inventing zero. Cancelling no-trade work and closing a partially executed remainder stay distinct. A newer event must not erase an older partial one; only new advisory application is fenced by proposal freshness.

No unresolved owner financial decision is required for this bounded linkage/status implementation. Automated tax/lot selection, tolerance-based completion, brokerage or automatic orders remain outside it. The plan is implementable after these corrections; this document is not a source-clear finding for future code or a runtime/concurrency validation.
