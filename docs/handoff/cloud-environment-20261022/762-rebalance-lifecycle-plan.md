## Existing contract and usable writers

The issue asks for one separate rebalance proposal after a monthly trend change or unchanged-trend quarter end, with actual holdings changed **only after owner-confirmed execution**. It warns that sales/buys may have fees and Austrian tax; it does not require an automatic lot selector, inferred tax figure, broker order, broker choice or proof of an optimal execution. Existing `strategyRebalance` (`packages/domain/src/wealth/strategy-plan.ts:241–264`) computes gross category buys/sells, a stable effective-date/trend ID, and gives a trend change precedence when quarter end coincides. `portfolioStrategyView` (`packages/db/src/repos/portfolio-strategy.ts`) derives that from a retained binding decision and complete classified EUR valuation; the strategy page displays it as non-executable and separate from the monthly contribution.

`createTrade` (`packages/db/src/repos/trades.ts:161–217`) already writes a user-specified buy/sell plus its investment-account settlement booking in one audited transaction/group. It accepts actual account, instrument, signed units, gross, fees and tax; the generic trade panel validates those entries and exposes Undo. The savings execution facade (`packages/db/src/repos/savings-plans.ts:360–409`, `apps/server/src/api/invest.ts:574–599`) shows the applicable pattern: recompute an open proposal inside the same transaction, compare the displayed proposal data, then call `createTrade(tx, ...)` with one audit group. Rebalance must remain separate from `savingsPlanId`/`savingsMonth`; those uniqueness rules describe a monthly savings-plan buy, not a multi-leg rebalance.

## Minimal accepted lifecycle

1. Keep the pure category gross proposal and contribution calculation unchanged. Give each effective **decision month** one canonical rebalance-event key within `app_setting`'s 64-character key limit, irrespective of whether its trigger is trend change or quarter end; retain the binding decision fingerprint **and decision audit revision**, trigger kind, source/valuation dates, strategy revision and four category amounts as a **historical proposal snapshot**. The current `${effectiveDate}:${trend}` display ID alone should not create a second event if a same-month decision is undone/re-recorded with corrected evidence or a different trend; even same-facts Undo/re-record changes the decision audit revision. A changed binding, configuration or valuation makes the **current projection** stale and requires fresh review; it must not prevent attribution of an actual trade executed against the earlier proposal. A completed/cancelled/partial event remains visible so the next GET cannot raise the same trigger as a fresh action. GET is read-only and must treat a missing event row with retained audit history as withdrawn/reviewable, never brand-new due.
2. A server-owned, strict versioned event record can use one audited `app_setting` key per decision month; no new migration is inherently required. The record holds trigger identity and proposal snapshot, explicit owner review state, linked live trade IDs with exact snapshots **and trade audit revisions**, per-link request intent and final outcome. Its revision must include current JSON **and audit-event count**, fencing Undo/redo ABA. Audit history, including physically removed rows and rolled-back updates, is also the request-id ledger: before a create/link/close, check retained audit evidence for that request ID and its immutable semantic intent, independent of refreshed CAS/source tokens. Include event key, action and exact trade ID in that intent. A retry of a committed live operation may return its receipt; a retry after Undo or with changed intent must report the prior undone/conflicting outcome, never recreate a trade or link. Do not rely solely on `trade.importKey`: its existing account-scoped duplicate lookup also sees undone/soft-deleted rows and does not validate matching amounts. Return the actual `groupId` for standard Undo of each event operation.
3. UI flow: from the separate rebalance card, open a proposal review with category deltas, binding trend/date and quote/FX/valuation provenance. If these sources are stale or missing, mark the **remaining projection** unavailable until refreshed. Keep the existing generic `TradePanel` as the authoritative manual capture of each actually executed buy/sell: the owner enters product, investment account, execution date, signed units, actual gross, fees and withheld tax. At attribution the owner explicitly reviews those actual fields, including a recorded tax of zero; a form default alone is not evidence that tax was zero. The strategy UI then lets the owner select that trade by exact ID and explicitly link it to the event, including a trade captured earlier or imported. A small optional callback that exposes the saved `result.trade.id` can make this handoff convenient without duplicating the trade form. If the generic post-save refresh fails, an already captured trade remains searchable for linking; the user must not be led to submit a second trade. Never prefill proposed amounts, fee or tax as proven execution. Show trade settlement separately from the monthly contribution; never create a savings-plan transfer or broker order. Generic trade save/Undo remain their own audited writer and group; linking does not write or alter the trade.
4. The link/confirmation API uses existing authentication and CSRF plus strict body validation. In one transaction, it checks event revision with audit count, request-id history, selected trade's exact ID/live state and investment-account scope, reviewed economic snapshot fields (account, security, date, kind, units, gross, fees, tax, deletion state and settlement link) **and trade audit revision**, plus existing trade/settlement invariants. A bounded **global** scan of every rebalance-event key's effective live links ensures the trade is not attributed to another event; refuse incomplete/oversized evidence rather than silently scanning only recent events. The owner explicitly confirms that this existing trade belongs to the event; never match by amount/date or infer historical intent. Persist the audited link without a new booking. Current quote/FX/target data are **not prerequisites** to capturing or linking an already executed actual trade; a changed binding does not erase the earlier event. If the separate current proposal projection is stale, only that projection is blocked/review-required. An event-link Undo removes only the link and leaves a pre-existing or separately captured trade untouched. Generic trade edit/delete/Undo and later redo of an old link must be detected against snapshots and global links on every read/action. For example, T linked to A, Undo A, T linked to B, Redo A makes **both** events `needs_reconciliation` and neither cleanly completed; further links/closure fail until explicit resolution. This read-derived fail-closed rule avoids changing generic Undo. The API returns the link audit group and new event revision.
5. Status is explicit and persistent: `reviewing` before a link, `partial` after one or more linked legs, `completed` only after the owner confirms the reviewed actual leg list, actual fees/tax and any remaining deviation or its present inability to be valued, `cancelled` when no trade was linked, and `partial_closed` when the remainder is abandoned after actual legs. No cent/percentage tolerance is invented to infer completion from target weights. A failed link leaves the captured trade intact and the event state unchanged, allowing explicit retry or selection of another existing trade; UI must say which operation succeeded. A pending/partial event is never represented as fully executed. An old open event remains visible when a newer monthly decision arrives; further links need the event's current revision and explicit owner confirmation rather than an automatic fresh trigger. On Undo/redo or other revision changes, require renewed intent instead of replaying an old request token.

## Narrow source seams and boundaries

- Domain: `strategyRebalance` only for event identity/trigger stability if needed; keep target/cent math. DB: add a strict strategy event/link facade near `portfolio-strategy.ts`, using existing `app_setting`/`audit_log` CAS and the existing trade read model; generic `createTrade` remains unchanged. Project the current proposal separately from audited historical event/linked-trade state, checking linked snapshots and cross-event uniqueness on every link/read. A stored advisory proposal review, if added, must compare exact canonical source inputs and revisions (positions/units, account cash/manual valuation, dated price/FX, exposure/classification/configuration and binding decision), not merely rounded totals or display dates. API: a small authenticated `/api/portfolio-strategy/rebalance/...` event/link/close facade in `apps/server/src/api/portfolio-strategy.ts`; generic `/api/trades` stays the actual capture path. Web: extend `apps/web/src/wealth/strategy-page.tsx` with event review, exact existing-trade picker/link and status, reusing the generic `TradePanel` save flow plus privacy, pending navigation, error/refetch and Undo. Optionally expose the returned trade ID from `TradePanel` to its caller. Do not alter generic savings-plan confirmation or broad trade schemas unless a concrete reviewer finding proves the app-setting attribution insufficient.
- Preserve actual trade date/currency rules, settlement bookings, existing holdings and Undo. Do not book proposal deltas, choose sale tax lots, estimate Austrian tax, accept missing tax as zero, or mark a broker execution verified. Changes in prices/FX/holdings/configuration/decision invalidate the **current projected remainder** and require another explicit look before a fresh proposal, while already captured actual trades and their explicit links remain reviewable. Review/read models must distinguish historical recorded trades from current projected targets.
- No unavoidable new owner product decision follows from the issue for this bounded manual lifecycle: actual product/account/units/gross/fees/tax and whether execution is finished are owner inputs. A later requirement for automated lot selection, tax computation, a numerical completion tolerance, brokerage, or backdated catch-up would be a separate policy decision. The trusted NDX/calendar provider and automated monthly scheduler remain independent open dependencies; existing retained binding decisions suffice to display this rebalance lifecycle.

Plan-review focus before edits: prove the one-event-per-month key against Undo/re-recording, app-setting CAS and audit-retained request IDs, global cross-event trade uniqueness, generic trade edit/Undo, the separation of stale projection from actual-trade attribution, multi-leg partial failure and whether an explicit schema relation becomes necessary. Independent source and executable validation are still required for any eventual implementation; #762 remains **NOT VALIDATED / NOT LIVE**.
