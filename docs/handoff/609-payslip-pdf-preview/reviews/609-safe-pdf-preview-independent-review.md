## Packaging: actual declaration versus optional availability

`apps/server/package.json` directly declares pdfjs-dist ^6.4.299, lock pins6.4.299. Its locked engine is >=22.13.0 or >=24: generic “Node22” alone does not prove engine compatibility, although existing project pins may satisfy it. Native `@napi-rs/canvas`1.0.10 and its platform packages are OPTIONAL transitive dependencies of PDF.js; the server does NOT directly declare canvas. Dockerfile71–72 explicitly copies both pdfjs-dist and the @napi-rs namespace, but copy instructions and lock entries do not prove native load/render success on x64/arm64. No installed PDF.js tree was available in this integration worktree; no fallback installation was attempted.

Smallest seam: use PDF.js's own Node canvas facility through the directly declared package. Do not introduce an undeclared direct canvas import based on incidental hoisting. If the actual implementation requires direct canvas APIs, declare that dependency explicitly through a separately approved manifest/lock change; do not quietly rely on its optional transitiveness. A missing renderer is a finite preview-unavailable response plus original download. NEW worker must be registered in the existing server build entrypoints and Docker COPY, leaving text extraction unchanged. pdfkit is DEV-only and is not a production rendering alternative.

## Concrete bounded authenticated rendering contract

- Reuse `/api/receipts/:id/pdf-preview` READ-ONLY POST, strict finite body `{page,password?,preset?}`, UUID path, live receipt MIME PDF and existing source15MiB limit. The existing global ordinary64KiB body limit is already sufficient for a bounded password/page body; do not add an upload exemption. It inherits originGuard, session guard, API no-store and safe global errors. A POST will also be refused during existing import holdWrites; preserve that behavior rather than bypass shared guards.
- Existing `verifyReceiptFile` checks SHA/size; render the SAME verified byte buffer, rechecking digest/length on the buffer passed into the worker if filesystem reading happens after verification. No caller filesystem path, remote URL, source hash path or raw library errors may enter the public interface. After async work re-read the live receipt identity/MIME/SHA/size before returning the PNG; source deletion or replacement must not publish stale output.
- One fixed page per request, at most existing30-document-page boundary; finite positive dimensions and rotation before surface allocation. A concrete initial implementation can cap each side2048 and total4,194,304pixels, output8MiB PNG, password length1024 and wall time20s. These are proposed engineering bounds, not existing accepted UI values or executed measurements. Set supported resolution presets rather than arbitrary scale. Check multiplication safely before allocation, and enforce equivalent caps for PDF.js intermediate/image canvas allocation, not just final export. PDF page count/text character limits alone do not bound decoded images.
- The existing `resourceLimits.maxOldGenerationSizeMb=128` bounds V8 heap, NOT native Canvas buffers, ArrayBuffer/external memory or whole-process RSS. Do not report it as a128MiB renderer-memory cap. Native decoder allocations require finite image/intermediate-canvas controls plus an explicit documented memory budget; if a hard memory boundary is claimed, it needs separately enforced OS/process isolation, not that existing worker-thread flag. Source-only review cannot establish this protection by copying the text worker. Fail unavailable if the chosen library path cannot enforce its bounded allocation contract; do not silently upscale or switch renderers.
- The proposal's “one in-flight render per review” is a CLIENT behavior, not server admission control. Add a small SERVER-WIDE per-process semaphore, initially1 render and no unbounded queue; concurrent requests return a finite busy response. Acquire before loading/copying source bytes to avoid concurrent15MiB buffers. Client close/AbortController must also cancel the actual server task where request cancellation is observable, with wall-time fallback; release capacity only after worker termination completes. A separate semaphore for every receipt/session is insufficient. Preserve existing extraction semantics; whether preview shares overall capacity with extraction is an explicit service-budget choice, not an accidental unlimited second worker pool.
- Worker accepts bytes/page/preset/password only. No PDF viewer, XFA/forms/annotation rendering, URL navigation, file attachment extraction, external asset URL or PDF action execution. Keep isEvalSupported:false and local packaged asset paths only. `useSystemFonts:false`/font flags need actual rendering validation; text extraction flags are not proof of readable raster output. Don't disable security flags or CSP to fix font fidelity. Whitelist fixed error classes (password/page/limit/busy/unavailable/source_changed), discard stdout/stderr and never forward stack/message/text/password, filenames or full worker payloads into application logs. Password/body values must not appear in query strings or diagnostic events.

## Private mode and minimal UI scope

One reusable receipt-local component, scoped CSS, and composition into existing PayslipIntake review/WideDialog are enough. Desktop left page/right actual review, phone stacked bounded page view and real44px page/zoom controls. Keep dirty draft/account/password/CAS/busy/retry semantics independent from preview errors.

Explicit open/page navigation creates only a current-page transient image. Current source/page generation must reject late stale responses; close, source switch, privacy ON and unmount abort the request, clear password/image bytes and remove the image subtree. Data-image URLs are permitted by current CSP, but still retain bytes in JS memory; no localStorage, React Query persistence, offline/service-worker cache, generated file, receipt row, audit row or server raster cache is added. Privacy ON shows only neutral preview-covered copy, not financial alt text, thumbnail, extracted text or blurred pixels. Existing explicit opaque original download remains a deliberate action; do not claim it is privacy-masked. Preview must never trigger reparse, automation, password remembering or payout confirmation. Reusing the existing sealed payroll password is valid only for the established payroll source context, never as a generic password oracle for every receipt.

Existing docs/receipts.md and docs/payslip-intake.md explicitly say PDFs are download-only. Update that narrow contract to say only generated inert PNG preview is supported; raw PDF remains attachment/octet-stream/nosniff. No CSP or public directory change is needed. Minimal preview ownership therefore includes new raster service/worker, receipts endpoint, server build/Docker worker copy, new web component/CSS, existing payslip review composition and these narrow docs/Roadmap. No DB/schema/financial writer change for preview.

## Payout normalization: sufficient evidence exists for a subset, not a source flag

Current manual `decidePayslipIntake` existing-booking path links receipt/expectation and deliberately leaves splits unchanged. NEW-booking path already derives salary=net−reimbursements, writes refund separately with the original signed rounding correction, and groups payout+payslip+receipt+expectation+inbox Undo. #741 exact existing-match planner refuses noncanonical lump allocations; retain that strict automatic contract.

Actual retained import evidence available in source:

- booking.source/importKey/importRunId; import_run source/status/mappingVersion and import group `import:<runId>`; ordinary importBooking also writes tracked creation.
- Audit entries contain full before/after booking and booking_split snapshots; history is ordered by original rowid, not timestamps. YNAB commit writes booking AND splits with tracked create events in that import group. All imported rows retain their real IDs. Current source flag survives later manual edits; status pending/confirmed and timestamps do not prove untouched state.

A separately authorized EXPLICIT normalization action can conservatively require: one actual selected source/intake + exact eligible current payout identity; valid parser/account/payee/date/currency/net/reimbursement evidence; known import creation of booking AND every split; original audited creation snapshots equal ALL current financial/split fields and identities; no later booking/split mutation, deleted/recreated original child, Undo/redo or conflicting payroll/expected/contact/transfer/trade/statement association; and current ordinary writer permissions (never implicit reconcile unlock). For a migration require actual committed import_run plus matching original import group, not a trusted-looking importKey prefix. For legacy/no-audit or bank sources with no proven equivalent lineage, keep Prüfen/manual editor. Thus no new persisted “untouched” boolean or migration is required to support a strictly proved subset, but no claim that every historical import is eligible is possible.

This provenance proof is NOT currently computed or exposed by `payslipMatches`/API: that function returns ID/date/amount/difference/exact and only checks for a salary-like split. Its “exact” means total amount, not source truth or canonical allocation. The automatic planner DTO likewise lacks import lineage. A NEW explicit action needs a server-owned eligibility/preview projection and full-ID/current source+booking+split+account+audit-head CAS, not a frontend inference or loosening of741. Re-read the entire proof inside the transaction before writing; ABA that returns identical values remains ineligible/stale.

If subsequently authorized, use ordinary `updateBooking` for the explicitly accepted salary/refund split replacement and existing intake decision/linking within ONE outer transaction and ONE audit group. Preserve original total/account/date/payee/native currency/status/import identity and unrelated metadata; no second payout, source mutation or report-side refund adjustment. Source/payslip/expected linkage and finance must all roll back on failure; Undo must restore original split IDs/allocations and all links exactly. Manually corrected, reconciled, custom-assigned or provenance-unknown records stay unchanged; already-exact ones use existing link-only path. Root must adjudicate the concrete future explicit-action scope; this review grants no new write.
