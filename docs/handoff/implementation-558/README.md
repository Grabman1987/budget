## Scope and data contract

- Four exact successful primary GET payloads enter `budget-offline-views` IndexedDB: `/api/heute?period=…&month=…`, unfiltered `/api/accounts`, the current-month `/api/budget/YYYY-MM`, and the first default latest-bookings page (`to` plus `limit=50`, no filters/cursor). Request path, timestamp, session generation and original integer-cent response are stored. No auth result, headers, credentials, other page, historic Plan or filtered bookings are stored. Failed GETs leave the prior successful row unchanged. A blocked device-store open cannot indefinitely delay an online read; after 500 ms that response is delivered live without snapshotting.
- The offline surface has read-only Heute source values including pace/day rows, account balance history/forecast, pinned envelopes, finance rules, attention and bookings; every account's native balance, reconciliation/valuation status and explicit unknown EUR flag; current-month Plan's carry/income/held/uncovered/overspend/unclassified totals and category rows; and latest bookings in server order with their source details. Each carries `Stand vom <Datum Uhrzeit>` from its own completed fetch. Plan rejects a saved prior month's key after month rollover. No dependent live queries are mixed into these rows and no missing valuation is calculated.
- Live routes stay mounted but hidden and inert after an in-session disconnect, retaining unsaved form fields. The shared request boundary rejects offline writes except the existing idempotent queued booking capture path. Cold offline starts mount only the static surface and queue capture. Other paths retain an offline notice with no financial view.
- A positive, nonfinancial `budget-offline-read-epoch` permission must match the IndexedDB generation for every offline read and save. Known authenticated status can create it only after an atomic physical clear succeeds. Sign-out removes it synchronously before the unchanged three-second clear attempt; an ordinary protected API 401 or authenticated-status HTTP 200 with `authenticated:false` starts the same cleanup. The latter preserves the normal login screen. A successful new login also revokes any previous session's permission before regrant. A quota failure on `setItem` grants no permission. A blocked clear can leave physical bytes unconfirmed, but a cold offline reload has no permission to show them; the next authenticated initialization tries the clear before granting access. Cross-tab revocation removes the permission and notifies both the app shell and already visible offline view in every open tab. Unsent text bookings retain #557 behavior.
